# Сравнение проекта с «Сервисы и AI-агенты v4»

Дата: 01.11.2026. Код: `f2f5ee9`. Источник требований: локальный HTML-файл «Cервисы и AI-агенты v4.html», 45 слайдов и приложения A–D.

После этой оценки локально добавлены три приоритетные доработки: бюджет активного времени/защита от одинаковых действий, ограниченная очередь GigaChat и диагностика ходов/инструментов. Их настройки описаны в README, проверки — в TESTING.md. Таблицы ниже сохраняют исходную оценку `f2f5ee9`; полноценные бюджеты токенов/стоимости, мониторинг и контроль общей ёмкости сервиса по-прежнему не реализованы.

Это проверка реализации по коду и имеющимся результатам проверок. Сервер заново не обследовался, нагрузочные и платные живые прогоны в рамках этого сравнения не выполнялись. Сведения о прошлых проверках взяты из [TESTING.md](TESTING.md) и [DEPLOYMENT.md](DEPLOYMENT.md).

## Вывод

У проекта уже есть важные инженерные границы: модель выбирает действия из ограниченного списка, код проверяет их допустимость и считает деньги, пользователь подтверждает существенные решения. Есть сохранение диалогов, резервные источники объявлений, модульные и сквозные проверки, включая реальные GigaChat и Циан.

Для хакатона и демонстрации это содержательный рабочий прототип. Готовность к промышленной эксплуатации пока не подтверждена: не хватает бюджетов выполнения, управления очередями и общей нагрузкой, измерений качества и стоимости, воспроизводимой оценки новых версий и постепенного выпуска.

### Надёжность

| Требование | Статус | Что есть и что остаётся |
| --- | --- | --- |
| Удалённые вызовы имеют таймауты | Частично | HTTP-клиенты задают таймауты; Циан имеет общий дедлайн 35 секунд, обогащение инфраструктурой — отдельный бюджет. Но HTTP-таймаут не покрывает всю цепочку повторов, получение токена и ожидание блокировок. Общего дедлайна хода/инструмента нет. |
| Повторы ограничены | Выполнено | `post_with_retry()` ограничивает попытки и повторяет сетевые ошибки, 429 и выбранные 5xx; обновление токена после 401 ограничено. У Циана ограничены переходы и есть пауза после отказа. Улучшения: случайная добавка к задержке, учёт `Retry-After`, единый бюджет повторов на ход. |
| Побочные эффекты идемпотентны | Частично | Повторное подтверждение уже закрытой карточки возвращает 409; объявления обновляются по ID, демонстрационные продукты учитываются по ключу. Для будущих реальных операций этого недостаточно. |
| Есть backpressure | Нет | Блокировка GigaChat ограничивает одновременную генерацию, но не число ожидающих запросов. Входящие сообщения и очереди SSE не имеют `maxsize`; нет ограничения числа активных агентов на весь процесс. Лимиты частоты по IP/аккаунту полезны, но не обеспечивают управление общей ёмкостью. |
| Есть load shedding | Нет | Есть 429 по частоте запросов. Нет отказа/отсрочки при переполнении общей очереди, нехватке свободных обработчиков или превышении времени ожидания, а также приоритетов для важных операций. |

| 39. Разветвление вызовов | Ограничены страницы, размер подборки и отдельные пачки инфраструктуры. Однако один поиск может породить несколько запросов Циана и много запросов 2GIS; итоговых счётчиков и глобальных квот на операцию нет. |
| 40. Пик после перезапуска | В текущем размещении один процесс, поэтому пример со 100 репликами напрямую не относится к демо. Для масштабирования не предусмотрены плавный прогрев и распределённое ограничение квот. `/api/health` проверяет наличие конфигурации LLM, но не успешность реального запроса к провайдеру; полноценной проверки готовности зависимостей нет. |
| 41. Управляемый отказ | Лимиты частоты есть; отказа по общей загрузке и приоритетов нет. |
| 42–45. Жизненный цикл и общая модель | Есть цикл «инцидент → исправление → регрессионный тест → выпуск». Его ещё нужно дополнить измерениями, эталонным набором, безопасным сравнением версий и ограничением мощности. |

## Приоритетные улучшения

1. **Ограничить активный ход агента.** Ввести единый бюджет времени, LLM-вызовов, инструментов, токенов и повторов. Включить ожидание очереди в дедлайн; остановку делать понятной пользователю. Время ожидания его решения учитывать отдельно. Проверить зависание, отмену и повторяющиеся ошибочные инструменты.
2. **Ограничить принимаемую работу.** Задать предел активных ходов и размера/возраста очереди GigaChat; при переполнении возвращать управляемый отказ. Ограничить очереди сообщений и SSE, число подписчиков и ресурсы распознавания речи. Не блокировать важные подтверждения из-за фонового обновления объявлений.
3. **Измерять каждый ход.** Сохранять идентификатор хода, commit/модель, вызовы и их задержки, ожидание очереди, токены, повторы, результат и оценку стоимости. Не записывать ключи и необработанные персональные данные в технические логи. Разделить работоспособность процесса и готовность обслуживать запросы.
4. **Упорядочить I/O и сохранение.** Общие HTTP-клиенты с закрытием при shutdown; общий лимит на провайдера; объединение совпадающих загрузок. Убрать неограниченное чтение истории. Для операций с последствиями — ключ идемпотентности и долговечный статус выполнения; при невозможности обязательной записи завершать действие ошибкой.
5. **Сделать проверку версий воспроизводимой.** Зафиксировать зависимости и манифест исполнения; расширить сценарии обезличенными инцидентами и эталонными результатами. Считать успешность по этапам и тяжесть ошибок. Сначала добавить безопасный replay, затем теневую проверку и постепенный выпуск по мере появления трафика.
6. **Проверить пределы измерениями.** Медленные модель/Циан/карты, одновременные диалоги, длинная история, большие аудиозаписи, холодный кэш и отказы БД. Измерить память и ожидание очереди. В `/api/stt` размер сейчас проверяется после чтения всего тела, поэтому для защиты памяти понадобится предел при приёме запроса или на reverse proxy.

Для демонстрации первыми полезны пункты 1–3. Перед настоящими банковскими действиями обязательны надёжное сохранение, идемпотентность, реальные полномочия интеграций и проверка сценариев отказа. Переписывание на multi-agent или переход с SQLite без измерений не заменяют этих механизмов.
